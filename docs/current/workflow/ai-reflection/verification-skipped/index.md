# 验证遗漏反思

本索引是 verification-skipped 类反思的可复用规则层。这里保留抽象规则、触发模式和边界条件；具体失败证据保留在下方事故样本文件中。

## 可复用规则

| 规则 | 适用场景 | 正确行为 | 依据样本 |
|------|----------|----------|----------|
| **对称修复必须两边验证** | 当代码中存在对称/镜像的处理路径（如 tracked diff vs untracked files、同步 vs 异步、读 vs 写），修复其中一个路径时，必须显式检查镜像路径是否存在相同缺陷。 | 修复后列出所有对称路径，逐条验证。若镜像路径无需相同修复，记录原因。 | [非对称安全阀遗漏](./2026-05-19-asymmetric-safety-valve.md) |
| **行为漂移三问** | 测试失败根因是"代码行为变更导致测试期望不匹配"时。 | 先回答：(1) 变更是哪个 commit 引入的？(2) commit message 是否明确说明了行为变更？(3) 如果未明确说明，先问用户是 bug 还是 feature，确认后再改测试。 | [盲目改测试适配行为漂移](./2026-05-26-blinded-test-adaptation.md) |
| **全量验证不可代理** | 子任务修复测试后声称通过时。 | 子任务可做单文件验证，但全量测试必须由编排者亲自运行，不能引用子任务的声称。 | [子任务修复引入新失败](./2026-05-26-trusted-subtask-report-without-independent-verification.md) |
| **子任务修复后必须独立全量验证** | 子任务报告测试通过后，orchestrator 在向用户汇报前必须亲自运行全量测试。 | 运行 `npm test` 或等效命令，将实际结果与子任务汇报对比。如有差异，以实际结果为准并向用户报告。 | [子任务修复引入新失败](./2026-05-26-trusted-subtask-report-without-independent-verification.md) |
| **测试失败方向选择必须经用户确认** | 测试失败可被解释为"测试过期"或"代码有 bug"两种方向时，不自动选择任何一方。 | 向用户说明两种方向的差异（工作量、风险、对下游任务的影响），等用户选择后再执行修复。 | [子任务修复引入新失败](./2026-05-26-trusted-subtask-report-without-independent-verification.md) |

## 触发模式

当出现以下模式时，AI 应先套用上方规则，再继续行动：

- 修复涉及 `if/else`、`diff vs files`、`read vs write`、`sync vs async`、`input vs output` 等对称结构
- 修复只改了一个分支/路径，另一个分支/路径在代码中位置邻近或语义对等
- 用户提到"为什么另一边没修"或运行后发现镜像路径仍有问题

## 边界规则

- 仅当对称路径的结构和语义确实对等时才适用——不同用途的路径不需要对称检查
- 如果镜像路径已完成相同的修复（或确认不需要修复），不算遗漏
- 本规则覆盖的是"修改时忘记检查镜像路径"，不覆盖"两边的修复都需要但只有一边能编译通过"这类技术限制
