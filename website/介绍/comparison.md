# 与竞品对比

## 诚实的声明

OpenFlow 不是最快的 AI 工作流，也不是最轻量的。它不会把“5 分钟开始写代码”作为第一目标。

它为另一类问题设计：当项目已经有历史包袱、生产约束、多人协作、AI Agent 切换和长期维护需求时，团队需要的不只是生成代码，而是边界、证据和追溯。

如果你的目标是一次性 Demo，OpenFlow 可能显得过重；如果你的目标是在复杂项目里安全地使用 AI 完成可审查变更，它的治理成本才有意义。

## 定位差异表

| 维度 | OpenSpec / GSD / 轻量规格工具 | OpenFlow |
|---|---|---|
| 核心目标 | 组织已明确目标的实现 | 澄清边界、约束行为、验证证据、归档追溯 |
| 启动速度 | 更快、更轻 | 更重，需要接受文档治理模型 |
| 最佳场景 | 新项目、原型、目标清晰的功能 | 棕地项目、模糊问题、高风险变更、团队协作 |
| 工作流重心 | 规格或计划驱动执行 | 澄清 → 设计 → 计划 → 实施 → 质量门 → 归档 |
| 完成定义 | 计划完成或代码完成 | readiness 通过并完成 archive |
| 长期知识 | 依赖团队额外维护 | current / decisions / archive 形成结构化记忆 |
| AI 约束 | 多为提示词或规格约束 | 文档作为行为契约，约束 AI 可行动范围 |

更准确的说法不是“OpenFlow 替代所有规格工具”，而是：

- 轻量规格工具更擅长让 AI 快速实现已明确目标。
- OpenFlow 更擅长让 AI 在复杂项目里完成受治理、可审查、可追溯的变更。

## 适用场景判断

### OpenFlow 更适合

- 棕地系统，有生产流量、历史行为和遗留约束。
- 团队需要把需求、设计、实现、验证和归档串成责任链。
- 变更完成后必须回答“为什么这样改”“验证证据在哪里”“影响了哪些代码”。
- AI 需要遵守项目长期事实，而不是只依赖当前对话上下文。
- 症状可能不是 Bug，而可能是数据异常、配置漂移、环境问题或需求语义不清。
- 质量门、归档证据和交接质量比首次输出速度更重要。

### 其他工具更适合

- 一次性 Demo、个人原型或探索性小项目。
- 目标已经非常清楚，只需要快速生成第一版代码。
- 团队不打算维护 `docs/current/`、`docs/changes/`、`docs/decisions/` 和 `docs/archive/`。
- “代码能跑”就是全部完成标准，不需要正式证据和归档权威。
- 项目规模较小，历史上下文和 Agent 切换成本可以忽略。

## 核心差异项表

| 差异项 | OpenFlow | 典型竞品 |
|---|---|---|
| 模糊问题处理 | 先调查、分类、澄清，再决定是否实施 | 常直接进入修复或生成 |
| 行为文档约束 | `current`、`changes`、`decisions`、`archive` 共同约束 AI | 多数以规格或提示词为主 |
| 质量门 | 证据验证、风险评估、readiness 分类 | 通常依赖人工检查或简单测试 |
| 归档追溯 | 归档冻结历史并生成 `implementation-mapper.md` | 通常没有正式追溯映射 |
| 长期事实维护 | 完成后提升必要事实到 `docs/current/` | 常停留在单次任务文档 |
| 漂移检测 | 基于合约标记的检查点式检测 | 通常没有，或需要外部机制 |
| AI 自我治理 | 可记录可复现的 AI 错误模式和反思 | 通常不覆盖 |
| Agent 切换 | 项目知识沉淀在目录结构中 | 更依赖当前会话或工具上下文 |

## 总结

选择工具的关键不是“哪个更先进”，而是你要治理什么风险。

- 如果你的主要目标是**快速把已知需求变成代码**，轻量规格或计划工具更顺手。
- 如果你的主要风险是**边界不清、AI 越界、证据不足、历史不可追溯、Agent 切换导致知识丢失**，OpenFlow 更适合。

OpenFlow 用更重的流程换取更强的工程确定性。它适合那些“写代码不是最难，确认该怎么改、如何证明改对、未来如何理解这次变更才最难”的项目。
