# 核心概念

概览页回答 OpenFlow 的 What 和 Why；本页回答 How：OpenFlow 如何用文档、目录、工作流和证据约束 AI 开发。

## 文档即约束编程

OpenFlow 的核心理念是：**文档编程就是约束编程**。

在普通项目里，文档经常只是给人看的说明；在 OpenFlow 里，文档会直接影响 AI 应该如何行动。AI 不只是“参考”文档，而是必须把文档当作当前项目的行为边界。

这带来一个重要变化：写文档不只是记录想法，而是在定义 AI 的可行动空间。

## 行为文档约束

行为文档约束（Behavioral Documentation Constraint）指的是：文档不仅描述系统，也约束 AI 的行为。

具体来说：

- 当前事实说明系统现在是什么样，AI 不得静默改变。
- 本轮变更设计说明这次允许改什么，AI 不得顺手扩大范围。
- 正式决策说明技术选择的边界，AI 不得绕过已有 rationale。
- 历史归档说明某些代码为什么存在，AI 不应把历史上下文当作可随意改写的草稿。

因此，OpenFlow 的文档不是“附属材料”，而是 AI 执行任务时必须遵守的契约。

## 目录划分

OpenFlow 用目录表达知识的生命周期：

| 目录 | 作用 | 生命周期 |
|---|---|---|
| `docs/current/` | 当前仍有效的事实、设计、规范和工作流约定 | 持续维护 |
| `docs/decisions/` | 跨 feature 的正式决策与 rationale | 长期稳定 |
| `docs/changes/` | 正在进行的 feature/change 工作区 | 完成后归档 |
| `docs/archive/` | 已完成变更的冻结历史与证据 | 只读权威 |
| `.sisyphus/` | OpenFlow / omo 的运行时状态、计划和验收文件 | 工作状态，通常不作为长期文档 |

这套划分的关键不是“把文件放整齐”，而是让 AI 明确知道：哪些是当前事实，哪些是进行中的设计，哪些是不可变历史，哪些只是运行时状态。

## 工作流模式

### Feature 工作流

Feature 是 OpenFlow 的主工作流，适用于新功能、需求修改、重构和技术债治理。

```text
brainstorm → feature → writing-plan → implement → quality-gate → archive
```

各阶段职责如下：

- `brainstorm`：可选的对话式探索，不生成正式文档，用于澄清意图和范围。
- `/openflow-feature`：形成设计边界和行为约束，生成 `design.md` 与 `behavior.md`。
- `/openflow-writing-plan`：把设计转成可执行计划，保存后停止，不直接写代码。
- `/openflow-implement`：创建实施记录，并在约束包内执行代码变更。
- `openflow-quality-gate`：实施后验证证据、评估风险、给出 readiness。
- `/openflow-archive`：冻结历史、更新 current 事实、生成追溯映射。

### Issue 工作流

Issue 用于边界模糊的问题调查，例如“线上偶现异常”“用户说行为不对”“某个数据看起来不一致”。这类问题不应该一开始就被当成 Bugfix。

Issue 的典型节奏是：

```text
issue → investigate → classify → decide → next step
```

它强调：

- 不预设问题类型。
- 调查阶段优先只读。
- 先确定系统应该是什么语义，再决定是否修改代码。
- 分类之后，必要时进入 Feature/implement/quality-gate/archive 的统一闭环。

## 合约标记与漂移检测

在 Feature 设计阶段，`design.md` 和 `behavior.md` 会表达一些关键约束：哪些行为必须保持，哪些边界不能越过，哪些验证结果代表成功。这些约束可以被转化为合约标记。

漂移检测用于回答：实现是否仍然符合设计？

OpenFlow 采用检查点式漂移检测，而不是持续监控：

1. 设计阶段生成合约标记。
2. writing-plan 中嵌入检查点任务。
3. 里程碑完成后进行语义检查。
4. 检查结果作为风险信号，不替代最终 quality-gate。

这样既避免每次保存都触发昂贵检查，也能在关键节点发现实现与设计的偏离。

## OpenFlow 回答的 3 个核心问题

OpenFlow 不追求让 AI 更快开始写代码，而是先回答三个问题：

1. **这次变更的边界是什么？**  
   哪些文件、行为、用户场景和系统语义属于本轮范围？哪些明确不属于？

2. **哪些事实、约束和行为不能被悄悄改变？**  
   当前系统已有约束、架构决策、兼容性要求、用户可见行为是否被保护？

3. **什么证据足以说明这次变更可以正式完成？**  
   需要哪些验证命令、测试、文档更新、风险复核和归档记录？

这三个问题分别对应边界、约束和证据，也是 OpenFlow 区别于普通“计划 → 执行”工具的地方。

## Issue 的当前位置

历史上，OpenFlow 曾把 Issue 作为一个更独立的入口来描述；当前文档不再把它推广为与 Feature 并列的第二条完成链路。

更准确地说：**Issue 是上下文能力，不是另一条与归档并列的完成链路。**

Issue 可以帮助 AI 在不确定场景下调查、分诊和澄清；但一旦需要修改代码、验证证据和正式关闭，仍然回到 quality-gate 与 archive 所定义的统一闭环。

## 完成的定义

在 OpenFlow 中，“完成”必须同时满足四个条件：

1. **实现符合设计和当前事实**：代码没有越过本轮变更边界，也没有静默破坏 `docs/current/` 或 `docs/decisions/` 中的约束。
2. **质量门给出允许归档的 readiness**：验证证据足够，风险被处理，或需要人工决策的问题已经解决。
3. **归档冻结历史并生成 `implementation-mapper.md`**：需求、设计、行为约束和代码位置可追溯。
4. **必要的长期事实被提升到 `docs/current/`**：完成后的系统状态不只存在于归档里，也反映到当前有效文档中。

少了其中任意一个，最多只能说“代码改完了”，不能说 OpenFlow 意义上的变更已经完成。
