# 需求变更

## 什么时候会用到

开发进行到一半，需求变了——这在真实项目中太常见了。可能是用户改了主意，可能是发现了新的约束，也可能是实现过程中发现设计有遗漏。

OpenFlow 不会要求你重新走一遍完整流程。你可以用 `/openflow-change` 在不丢失已有上下文的情况下调整范围。

## 怎么用

```text
/openflow-change 添加用户资料页 "把头像改成方形裁剪，同时增加昵称字段"
```

命令格式：

```text
/openflow-change <需求名> "变更描述"
```

- **需求名**：当前正在进行的需求名称。
- **变更描述**：用引号包裹，说清楚要改什么。

## 它会做什么

运行后，AI 会：

1. **找到当前的设计文档**，确认工作区还在进行中。
2. **记录变更意图**，把你的变更描述附加到当前状态中。
3. **按"文档优先"的顺序更新**：先更新 `design.md`，再更新 `decisions.md` 和 `prd.md`（如果有的话），最后调整代码。
4. **提示你重新验证**：变更完成后需要重新跑质量门和归档。

::: tip 核心原则：文档先于代码
需求变更时，OpenFlow 要求先更新设计文档，再改代码。这样保证文档和代码始终一致，而不是代码改完了文档还停留在旧版本。
:::

## 注意事项

| 情况 | 说明 |
|---|---|
| 需求已经归档了 | 不能用 `/openflow-change`，归档内容不可修改，需要开新需求 |
| 需求已经通过质量门 | 可以变更，但变更后需要重新验证 |
| 变更影响范围很大 | 建议让 AI 评估是否需要拆分成独立需求，而不是塞进当前需求里 |
