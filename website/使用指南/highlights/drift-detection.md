# 漂移检测

## 是什么

漂移检测用于发现代码、设计和文档之间随时间产生的不一致。它由 Diff Engine、Guardian Consumer 和 Repair Coordinator 协作完成。

Diff Engine 负责识别变化，Guardian Consumer 负责消费检查结果并判断风险，Repair Coordinator 负责协调可修复问题的处理。

## 为什么需要它

设计和实现不会永远同步。文件会改名，符号会移动，计划会更新，历史约束也可能被新实现无意破坏。如果没有漂移检测，系统会逐渐出现“文档说的是一套，代码做的是另一套”的问题。

漂移检测让这些不一致在关键节点被发现，而不是等到用户报告、集成失败或归档审查时才暴露。

## 如何使用

漂移检测基于检查点运行，不是持续监控。典型流程是：

1. 设计阶段生成合约标记和关键映射
2. 在里程碑节点运行检查
3. 对发现的漂移进行分类
4. 对确定性漂移执行自动修复或生成修复建议

可自动修复的情况通常包括文件重命名、符号重命名等确定性变化。是否允许自动修复可通过配置控制：

```json
{
  "guardian": {
    "auto_fix": true
  }
}
```

对于语义不明确或需要产品判断的漂移，系统会保留为人工决策项，而不是盲目修改。

## 与其他机制的关系

漂移检测与 [契约扫描](./contract-scanning) 协作：契约扫描告诉系统已有约束是什么，漂移检测检查这些约束和当前实现是否仍然一致。

它与 Quality Gate 相互独立。Quality Gate 关注当前变更是否可交付，漂移检测关注设计、契约和实现是否随时间保持一致。
