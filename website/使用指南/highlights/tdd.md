# TDD（测试驱动开发）

## 是什么

TDD 是以 Red-Green-Refactor 为核心的开发循环：先写一个描述预期行为的失败测试，再实现刚好足够的代码让测试通过，最后在测试保护下整理结构。

在 OpenFlow 中，TDD 不是附加建议，而是计划生成阶段会被注入到实现任务中的工作方式。它要求在关键逻辑真正落地之前，先把“正确行为”变成可执行的测试。

## 为什么需要它

AI 很容易直接进入实现，先写出看似完整的代码，再用少量验证补充信心。这样会导致预期行为没有被明确表达，边界条件和失败路径也容易被遗漏。

TDD 通过“先测试、后实现”强制定义目标行为。没有它，算法、数据模型、业务规则、状态机和认证逻辑这类核心领域，很可能只依赖自然语言说明和人工审查来保证正确性。

## 如何使用

默认情况下，TDD 已开启。也可以在配置中显式声明：

```json
{
  "tdd": {
    "enabled": true
  }
}
```

当生成开发计划时，OpenFlow 会自动注入 TDD 任务，要求实现前先补充或更新测试。以下领域应优先使用 TDD：

- 算法与计算逻辑
- 数据模型与转换规则
- 业务规则与权限判断
- 状态机与流程分支
- 认证、授权等安全相关逻辑

如果确实不适合用单元测试驱动，需要在计划或执行记录中说明原因，并提供等价的验证方式。

## 与其他机制的关系

TDD 与 [BDD 与集成测试](./bdd) 互补：TDD 更关注单元级逻辑是否正确，BDD 更关注用户可见行为和端到端流程是否成立。

TDD 也与 [金字塔原则编程](./pyramid) 协作。金字塔原则帮助拆分抽象层级，TDD 则为每一层的关键规则建立可执行保护。
