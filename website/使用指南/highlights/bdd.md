# BDD 与集成测试

## 是什么

BDD 是从行为出发的验证方式。在 OpenFlow 中，Feature 阶段会把用户可见的行为写入 `behavior.md`，并使用 Given / When / Then 场景描述前置条件、触发动作和期望结果。

这些行为场景不会停留在文档层面。它们会转化为证据要求，并在 Quality Gate 中通过集成测试、运行结果或其他可核验证据进行确认。

## 为什么需要它

单元测试能证明局部逻辑正确，但不一定能证明用户真正关心的流程正确。例如多个模块组合后的交互、配置生效路径、CLI 命令输出、文档承诺和实际行为之间的关系，都可能逃出单元测试覆盖范围。

如果没有 BDD，系统可能出现“每个函数都通过测试，但整体行为不符合需求”的问题。BDD 让验收标准变成可追踪、可验证的行为证据。

## 如何使用

在 Feature 阶段，OpenFlow 会自动在 `behavior.md` 中生成或维护行为场景。每个场景通常包含：

- Given：已有上下文或初始状态
- When：用户动作、命令或系统事件
- Then：可观察的结果

场景会按优先级跟踪：

- `critical`：必须验证，缺失证据会阻止 Ready
- `normal`：应验证，通常需要测试或明确证据
- `optional`：可选验证，适合补充覆盖或非关键体验

Quality Gate 会检查这些场景是否有对应证据，例如集成测试、命令输出、截图、日志或人工可复核说明。

## 与其他机制的关系

BDD 与 [TDD](./tdd) 互补：TDD 面向单元级规则，BDD 面向跨模块行为和用户可见结果。

BDD 直接连接 `behavior.md` 中的验收标准，并会影响 [代码地图](./code-map) 中“行为场景 → 代码”的可追溯映射。
