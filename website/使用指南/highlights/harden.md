# 对抗性硬化

## 是什么

对抗性硬化是一种从攻击者视角审查实现的机制。它不只问“代码是否看起来合理”，而是主动寻找实现是否偏离设计、证据是否不足、边界是否被忽略。

它的目标是发现普通自查容易放过的问题，尤其是那些在 happy path 中不明显、但会在真实使用或后续维护中放大的风险。

## 为什么需要它

AI 的自我审查常常偏表面：检查语法、确认文件存在、简单运行测试，然后就认为完成。但真正的问题可能藏在规格理解、行为一致性、契约约束、回归路径和证据完整性中。

没有对抗性硬化，高风险变更可能在“看起来可用”的状态下进入后续流程，直到集成、归档或用户使用时才暴露更深层的问题。

## 如何使用

对抗性硬化通常由高风险变更自动触发。常见触发条件包括：

- 变更文件数大于或等于 3
- diff 行数大于或等于 50
- 涉及敏感路径、配置、权限、状态机或关键流程
- Quality Gate 判断需要更强证据

审查会围绕 6 类发现展开：

- 行为违规
- 规格违规
- 意图偏差
- 契约分歧
- 回归风险
- 证据缺失

每个发现会被归入 4 类处置之一：

- `actionable`：需要立即修复
- `ambiguous`：需要澄清或补充判断
- `nonBlocking`：记录但不阻塞当前完成
- `style`：风格或表达问题

可通过配置限制硬化轮次和单个发现的争议轮次：

```json
{
  "harden": {
    "maxRounds": 2,
    "maxArgumentRoundsPerFinding": 2
  }
}
```

## 与其他机制的关系

对抗性硬化通常由 Quality Gate 触发，并将发现反馈给实现过程进行修正。

它也会补强 [BDD 与集成测试](./bdd) 和 [契约扫描](./contract-scanning) 的结果：BDD 提供行为证据，契约扫描提供已有约束，硬化负责从反面验证这些内容是否真的被满足。
